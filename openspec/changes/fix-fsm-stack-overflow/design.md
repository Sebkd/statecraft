# Design: fix-fsm-stack-overflow

> **Статус**: Черновик
>
> **Дата**: 2026-08-20

---

## D1. Что именно меняется в кодогенерации

Изменение точечное: один узел в построении плеча `match`. Всё остальное —
разбор нового флага и проброс его до этого узла.

### D1.1 — `attrs.rs`: разбор флага

`OnAttr` получает поле `boxed: bool`. В `parse_on` добавляется ветка на
**path-only** ключ (без `= value`):

```rust
} else if meta.path.is_ident("boxed") {
    boxed = true;
} else {
    return Err(meta.error(
        "unsupported #[on] key (expected state, event, next, boxed)",
    ));
}
```

Сообщение об ошибке для неизвестного ключа обновляется — оно и обеспечивает
критерий приёмки №8 (опечатка `boxxed` даёт внятную ошибку с указанием места).

### D1.2 — `Cargo.toml`: возможность сборки `boxed-all`

Та же схема проброса из фасада в макро-крейт, что уже используется для
`public-emit` и `tokio`:

```toml
# Cargo.toml (фасад)
[features]
boxed-all = ["statecraft-fsm-macros/boxed-all"]
diagnostics = ["statecraft-fsm-macros/diagnostics"]

# statecraft-fsm-macros/Cargo.toml
[features]
boxed-all = []
diagnostics = []
```

Внутри `codegen.rs` политика читается ровно как читается `public-emit` —
`cfg!(feature = "boxed-all")`, вычисляемый **при сборке макро-крейта**. Новых
ключей у `#[fsm]` не появляется, `statecraft-fsm-macros/src/lib.rs` не меняется.

### D1.3 — `codegen.rs`: обёртка вызова

В замыкании, строящем плечи (`let arms = handlers.iter().map(|h| { … })`),
вызов обработчика формируется в одном месте и используется дважды — в
fallible-ветке и в инфаллибл-ветке. Обе переводятся на общий узел:

```rust
let boxed_all = cfg!(feature = "boxed-all");
// …
let __call = if h.on.boxed || boxed_all {
    quote! { ::std::boxed::Box::pin(self.#method(#call_arg)) }
} else {
    quote! { self.#method(#call_arg) }
};
```

Далее — как сейчас: инфаллибл-ветка даёт `#__call.await`, fallible-ветка —
`match #__call.await { Ok(__v) => __v, Err(__e) => return … }`, по-прежнему
внутри `quote_spanned!{h.span=> …}`, чтобы диагностика несовпадения типа ошибки
осталась на обработчике.

**Почему боксируется именно вызов, а не тело `__apply_one` целиком.** Плечи
`match` — независимые точки в раскладке корутины. Боксирование одного плеча
убирает из раскладки только его, остальные остаются inline. Это и даёт
выборочную политику (§2.2 change.md), недостижимую при обёртке `__apply_one`
целиком: там боксирование либо есть для всех переходов, либо нет ни для одного.
Оптовая политика при этом получается бесплатно — тем же узлом, с `boxed_all`
в условии.

### D1.4 — `model.rs`

Не меняется. Отдельного поля в `Handler` не требуется: флаг живёт в `OnAttr`,
который `Handler` уже содержит (`h.on.boxed`).

### D1.5 — `std` vs `alloc`

Крейт уже безусловно зависит от `std` (`std::collections::VecDeque` в
сгенерированной структуре, `std::sync::Arc` в Tokio-адаптере). `::std::boxed::Box`
новых ограничений не вносит. Если появится задача на `no_std + alloc`, обе
конструкции переезжают на `::alloc::` одновременно — это отдельный change.

### D1.6 — Auto-traits

`Box::pin(fut)` даёт `Pin<Box<F>>`, где `F` — конкретный тип future обработчика,
не `dyn Future`. Автотрейты (`Send`, `Sync`) выводятся как и раньше, никаких
`+ Send` в границах не появляется. `Machine::spawn` продолжает требовать `Send`
через существующие `where`-клаузы, и требование выполняется тем же способом.
Это проверяется существующим `tests/tokio_adapter.rs`.

## D2. Взаимодействие с существующими возможностями

| Возможность | Взаимодействие |
|---|---|
| Обработчики с payload (`event = Foo(Type)`) | Ортогонально: `#call_arg` подставляется внутрь `Box::pin(...)` без изменений |
| Fallible-обработчики (`Result<_, E>`) | Ортогонально: боксируется вызов, `match` по результату остаётся снаружи, `ApplyError::Handler` строится как прежде |
| Ветвящиеся переходы (`next = [A, B]`) | Ортогонально: боксируется вызов, отображение `Next`-enum → состояние остаётся снаружи |
| Self-emit (`emit` / `emit_replace`) | Не затрагивается. Очередь и порядок каскада — свойство `__drive`, а он не меняется. FIFO/breadth-first сохраняется |
| `STATECRAFT_CASCADE_LIMIT` | Не затрагивается |
| Tokio-адаптер (`spawn`/`Handle`) | Выигрывает автоматически: future задачи содержит `apply`, а тот больше не содержит тела помеченных обработчиков |
| `channel_size` | Не затрагивается |
| `public-emit` | Ортогонально: разные оси. Комбинация проверяется в `--all-features` |

## D3. Совместимость

Обе оси аддитивны.

- **Атрибут.** `#[on]` без `boxed` разворачивается в те же токены, что и в 0.1.7.
- **Возможность сборки.** `boxed-all` выключена по умолчанию. Включение не
  меняет ни одного наблюдаемого поведения — только место размещения тела
  обработчика; это требование к feature, а не пожелание, и оно закреплено
  критерием приёмки №6.

Отсюда следует, что обратная совместимость не требует отдельного «режима
совместимости»: политика по умолчанию без пометок **и есть** поведение 0.1.7.
Это фиксируется критерием приёмки №3 и проверяется тем, что существующий набор
тестов проходит без единой правки.

Матрица сборок, которую обязан покрывать CI:

| Сборка | Что проверяет |
|---|---|
| `cargo test` | политика по умолчанию, ни один переход не помечен — эквивалентность 0.1.7 |
| `cargo test --features diagnostics` | замеры размера future (D5.1) |
| `cargo test --features boxed-all,diagnostics` | оптовая политика (критерии 4–6) |
| `cargo test --all-features` | все оси вместе, включая `tokio` и `public-emit` |

Версия: minor bump (0.2.0) — новая возможность, ломающих изменений нет.

## D4. Диагностика: как измерять, а не гадать

Ключевой урок расследования: у потребителя не было способа **измерить**
размер future, поэтому обходной путь применили вслепую и не смогли проверить
результат. Изменение обязано этот способ дать.

### D4.1 — Генерируемая функция замера

Под новой feature `diagnostics` в `impl #fsm_name` генерируется:

```rust
/// Фактический размер future, возвращаемого `apply`, в байтах.
/// Future создаётся и уничтожается без единого poll — побочных эффектов нет.
pub fn apply_future_size(&mut self, event: #event_enum) -> usize {
    let __f = self.apply(event);
    let __n = ::core::mem::size_of_val(&__f);
    ::core::mem::drop(__f);
    __n
}
```

Корректность отбрасывания: future от `async fn` до первого `poll` не выполнил
ни строки тела, его `drop` — no-op над захваченными аргументами.

Это позволяет потребителю поставить в CI утверждение вида:

```rust
#[test]
fn dispatch_frame_stays_bounded() {
    let mut fsm = InboundCommonFsm::new(ctx());
    assert!(fsm.apply_future_size(Event::Timeout) < 4096);
}
```

и ловить регресс при добавлении нового тяжёлого перехода — на этапе тестов,
а не падением пода. Это же закрывает критерии приёмки №1 и №2.

### D4.2 — Процедура для потребителя, у которого фикс «не помог»

`sepia/process-driver` обернул 26 обработчиков вручную, и stack overflow
остался. Синтетический стенд показывает, что механика работает, значит
переполняется другой участок. Порядок разбирательства:

1. Замерить `apply_future_size` для каждой FSM. Если < ~4 КБ — **FSM не при чём**,
   и дальнейшие обёртки бессмысленны.
2. Если велик — найти обработчик, тело которого обёрнуто не целиком (локалы,
   объявленные до `Box::pin`, остаются в раскладке внешней future).
3. Если FSM ни при чём — искать вне её. Кандидаты в порядке убывания
   вероятности: future, передаваемая в `tokio::spawn` из тела обработчика;
   ветки `select!` в долгоживущих циклах; глубоко вложенные комбинаторы
   (`join_all` по большому вектору); рекурсия в бизнес-логике.
4. Точное место даёт `RUST_MIN_STACK`-бисекция по subprocess'у либо
   `-Z print-type-sizes` на nightly-сборке того же кода (toolchain для замера
   может отличаться от продового — размеры корутин не зависят от канала).

Пункты 1–2 — то, ради чего добавляется D4.1. Пункты 3–4 — вне statecraft;
фиксируются в change потребителя, не здесь.

## D5. Тестирование

### D5.1 — Размер future (основная проверка, детерминированная)

`tests/boxed_dispatch.rs`, с возможностью `diagnostics`. Эталонная FSM: один
обработчик, удерживающий `[u8; 512 * 1024]` через `await`.

Политика по умолчанию (без `boxed-all`):

- переход помечен `boxed` → `apply_future_size` < 256 Б;
- переход не помечен → `apply_future_size` > 512 * 1024 (фиксирует, что
  умолчание действительно ничего не боксирует);
- смешанная FSM (тяжёлый помечен, тривиальный нет) → < 256 Б, тривиальный
  переход выполняется корректно.

Оптовая политика (`--features boxed-all`, файл под `#[cfg(feature = "boxed-all")]`):

- ни один переход не помечен → < 256 Б (критерий приёмки №4);
- часть переходов помечена → < 256 Б, поведение то же (критерий приёмки №5).

Пороги — абсолютные, в байтах, а не «меньше, чем без фикса»: иначе тест
зелёный, когда оба результата одинаково плохи.

Отдельный тест на семантическую нейтральность (критерий приёмки №6): один и тот
же сценарий каскада с ветвлением, ошибкой обработчика и payload прогоняется в
обеих сборках и сверяется по последовательности состояний и значению ошибки.

### D5.2 — Фактический стек (подтверждающая проверка)

Переполнение стека завершает **процесс**, а не тест, поэтому проверка идёт
через subprocess: тест перезапускает собственный бинарь с переменной окружения
и проверяет код возврата.

- Поток со `stack_size = 64 КБ`, обработчик с локалами 3 × 512 КБ, переход
  боксируется (любой из двух политик) → штатное завершение.
- То же, когда переход не боксируется ни одной политикой → аварийное завершение
  (закрепляет, что тест из D5.1 измеряет то, что действительно ломается).

Помечается `#[ignore]`, если на каком-то из целевых CI-раннеров окажется
нестабильным: основной контракт закрывает D5.1.

### D5.3 — Компиляционные ошибки (trybuild)

- `tests/ui/unknown_on_key.rs` — `#[on(..., boxxed)]` → ошибка со списком
  допустимых ключей (критерий приёмки №8).
- `tests/ui/unknown_fsm_key.rs` — `#[fsm(initial = A, boxed_dispath)]` → то же
  для `#[fsm]`.

### D5.4 — Регресс существующего поведения

Вся матрица сборок из D3 — без правок в существующих тестах. Любая правка в
`tests/*.rs`, кроме новых файлов, означает нарушение обратной совместимости
(критерий приёмки №3).

### D5.5 — Замеры, воспроизводящие таблицы из change.md

Стенд, на котором получены цифры §1 и §2.4 change.md, оформляется как
`examples/stack_frame.rs` — чтобы утверждения о 24 704 Б / 4,9 нс / 22,4 нс
можно было перепроверить, а не принимать на веру. Пример печатает размеры и
время для обеих политик, поэтому собирается с `--features diagnostics`.
