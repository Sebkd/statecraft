## 1. Предложение

### Цель изменения

Сделать так, чтобы обработка одного события FSM потребляла **ограниченный кадр стека,
не зависящий от размера тела самого тяжёлого обработчика**. Сегодня зависимость прямая
и линейная: один «толстый» обработчик поднимает стоимость стека для всей машины.

Потребитель (`sepia/process-driver`) падает на K8s:

```
thread 'tokio-rt-worker' (7) has overflowed its stack
fatal runtime error: stack overflow, aborting
```

### Корневая причина

`#[fsm]` генерирует цепочку `apply → __drive → __apply_one → <обработчик>`. Все четыре —
`async fn`, то есть их future **вложены по значению**: future обработчика физически
лежит внутри future `__apply_one`, тот — внутри `__drive`, тот — внутри `apply`, а `apply`
— внутри future задачи, которую создаёт `spawn`.

Замер на синтетическом стенде (release, rustc 1.96.1, arm64):

| Что | Размер |
|---|---|
| Один обработчик с локалами 3 × 8 КБ, живущими через `await` | ~24 576 Б |
| `size_of_val` future от `apply` для FSM из **8** таких обработчиков | **24 704 Б** |

Два вывода, оба важные:

1. **Размер не суммируется по переходам** — это `max`, а не `sum`. Раскладка корутины
   переиспользует слоты между плечами `match`, которые никогда не живы одновременно.
   Гипотеза «23 перехода × тяжёлый обработчик» **неверна**.
2. **Собственные накладные расходы диспетчера statecraft — ~128 байт** на все три слоя
   (`apply` + `__drive` + `__apply_one`). Библиотека почти ничего не добавляет сверх
   самого тяжёлого обработчика — но и не изолирует его.

Соответственно, размер future масштабируется вместе с телом обработчика, а требуемый
стек — примерно вдвое от размера future (future создаётся на стеке вызывающего и лишь
затем переносится в аллокацию задачи):

| Локалы в обработчике | `size_of_val(apply)` | Минимальный `stack_size` потока |
|---|---|---|
| 3 × 8 КБ | 24 704 Б | 64 КБ (32 КБ → crash) |
| 3 × 64 КБ | 196 736 Б | 1 МБ (256 КБ → crash) |
| 3 × 512 КБ | 1 572 992 Б | 4 МБ (1 МБ → crash) |

### Почему обходной путь на стороне потребителя — не решение

Известный обходной путь — обернуть тело каждого обработчика в `Box::pin(async move { … }).await`
вручную (так сделано в `sepia/openspec/changes/fix-fsm-stack-overflow`). Замер подтверждает,
что механика работает: на том же стенде future `apply` падает с 24 704 Б до **104 Б**, а
минимальный стек — с 64 КБ до 16 КБ.

Но как решение уровня продукта оно негодное:

- **Не масштабируется дисциплиной.** Требует помнить про обёртку в каждом новом обработчике
  каждой FSM. Один забытый `Box::pin` возвращает исходный размер целиком — потому что размер
  считается по `max`.
- **Ничем не проверяется.** Ни компилятор, ни clippy, ни тесты не ловят пропуск.
- **Лечит симптом у потребителя, а причина — в форме кодогенерации.** Это ответственность
  библиотеки: именно она решает, как обработчик попадает в future задачи.

Отдельно зафиксировано (замер, а не рассуждение): опасение «`Box::pin` всё равно строит
future сначала на стеке, поэтому пик не изменится» **не подтвердилось**. В release-сборке
временный объект элидится вплоть до future размером 1,5 МБ — стек в 64 КБ выдерживает.

### Инициатор

Stack overflow при запуске `process-driver` на K8s. Ручной `Box::pin` в 26 обработчиках
проблему у потребителя не снял — что означает, что там переполняется **другой** участок
стека и его нужно сначала измерить (процедура — в `design.md`, D4). Настоящее изменение
закрывает ту часть, которая действительно принадлежит statecraft.

### Затронутые компоненты

- [x] `statecraft-fsm-macros/src/attrs.rs` — разбор флага `boxed` в `#[on(...)]`
- [x] `statecraft-fsm-macros/src/codegen.rs` — обёртка вызова в плече `match`
- [x] `Cargo.toml` (оба) — возможности сборки `boxed-all` и `diagnostics`, проброс в макро-крейт
- [x] `src/lib.rs`, `README.md` — документация возможностей и пометки

- [ ] `statecraft-fsm-macros/src/model.rs` — не требуется: флаг живёт в `OnAttr`
- [ ] Тела обработчиков пользователя — **не трогаем** (в этом весь смысл)

### Приоритет

Высокий. Потребитель не запускается в проде, а обходной путь неустойчив к регрессу.

### Обратная совместимость

Полная, по обеим осям. Без пометок переходов и с выключенной возможностью
сборки кодогенерация байт-в-байт прежняя — политика по умолчанию **и есть**
поведение 0.1.7 (критерий приёмки №3). Включение возможности `boxed-all` не
меняет ни одного наблюдаемого поведения, только место размещения тела
обработчика (критерий приёмки №6). Публичный API (`apply`, `emit`, `spawn`,
`Handle`, `ApplyError`) не меняется. Каскад self-emit (FIFO, breadth-first) не
затрагивается.

## 2. Решение

### 2.1. Две политики размещения, выбор — возможностью сборки

Вводятся ровно две политики того, где живёт тело обработчика при
диспетчеризации. Политика выбирается возможностью сборки (Cargo feature)
`boxed-all`:

| Политика | Как включается | Что боксируется | Кому |
|---|---|---|---|
| **Выборочная** (по умолчанию) | ничего включать не нужно | только переходы, помеченные `#[on(..., boxed)]` | всем: полный выигрыш по стеку там, где он нужен, нулевая цена на остальных переходах |
| **Оптовая** | `features = ["boxed-all"]` | все переходы всех FSM крейта | когда переходов много, все они I/O-bound, и разбираться, какой тяжёлый, дороже, чем заплатить аллокацией везде |

Третьей политики («не боксировать ничего») нет: она совпадает с выборочной,
если ни один переход не помечен. Это и есть текущее поведение 0.1.7 — то есть
обратная совместимость обеспечивается не отдельным режимом, а тем, что политика
по умолчанию без пометок ничего не меняет.

### 2.2. Выборочная политика: `#[on(..., boxed)]`

```rust
#[on(state = Running, event = Timeout, next = [Timeout, Finished], boxed)]
async fn on_running_timeout(&mut self) -> RunningTimeoutNext { … }
```

Кодогенерация оборачивает **вызов** обработчика в его плече `match`:

```rust
// непомеченный переход — как сегодня
(State::Idle, Event::Tick) => { self.on_tick().await; … }
// помеченный переход
(State::Running, Event::Timeout) => { let __next = Box::pin(self.on_running_timeout()).await; … }
```

Future обработчика уезжает в кучу, в раскладке диспетчера от него остаётся
указатель. Тела обработчиков не меняются — в этом весь смысл по сравнению с
ручной обёрткой.

### 2.3. Оптовая политика: возможность сборки `boxed-all`

```toml
statecraft-fsm = { version = "0.2", features = ["boxed-all"] }
```

Боксируются все переходы; пометки `#[on(..., boxed)]` при этом избыточны, но
безвредны — остаются как документация намерения и продолжают работать, если
возможность позже выключат.

Возможность **аддитивна и семантически нейтральна**: её включение не меняет ни
одного наблюдаемого поведения — ни порядка каскада, ни семантики ошибок, ни
типов, — только место размещения тела обработчика. Это ровно то свойство,
которого Cargo требует от feature, и оно снимает обычное возражение против
выбора поведения фичой: при унификации по графу зависимостей (кто-то в дереве
включил `boxed-all` — включилось у всех) худший исход — все переходы
боксированы, то есть медленнее на ~18 нс и надёжнее по стеку. Некорректной
сборки такое включение породить не может.

Остаточный риск фиксируется честно: потребитель с горячей in-memory FSM может
получить замедление из-за флага, включённого не им. Смягчение — раздел про
это в README и в rustdoc возможности, чтобы место, где искать, было очевидным.

### 2.4. Почему по умолчанию выборочная, а не оптовая

Боксирование стоит аллокации на переход. Замер, тривиальный обработчик
(`n += 1`), 5 млн переходов:

| Политика | `size_of_val(apply)` | нс/переход |
|---|---|---|
| Сегодня (0.1.7) | 96 Б | **4,9** |
| Оптовая (`boxed-all`) | 80 Б | 22,4 |
| Выборочная, переход не помечен | 96 Б | **7,1** |

Для обработчика, который ходит в БД/HTTP (миллисекунды), +18 нс не существуют.
Для in-memory FSM в горячем цикле это учетверение стоимости перехода. Делать
такую цену умолчанием для всех существующих пользователей нельзя.

Решающий замер — смешанная FSM (один тяжёлый переход + один горячий тривиальный):

| Вариант | `size_of_val(apply)` | нс на тривиальный переход |
|---|---|---|
| Сегодня | 24 704 Б | 7,5 |
| Оптовая | 88 Б | 20,8 |
| **Выборочная, помечен только тяжёлый** | **96 Б** | **7,1** |

Выигрыш по стеку выборочная политика берёт целиком — 24 704 → 96 Б, столько же,
сколько оптовая, — а за горячий путь не платит ничего. Поэтому она и выбрана
умолчанием; оптовая существует для случая, когда помечать переходы поштучно
дороже, чем заплатить везде.

### 2.5. Диагностика

Замер размера future не должен требовать сборки синтетического стенда, как
потребовалось здесь. Генерировать под возможностью сборки `diagnostics`
функцию, возвращающую фактический `size_of_val` future от `apply` — чтобы это
можно было утверждать тестом в CI потребителя, а не обнаруживать падением пода.
Детали — `design.md`, D4.

## 3. Альтернативы (отклонены)

| Вариант | Почему отклонён |
|---|---|
| Боксировать всё **безусловно**, без выбора | Замерено: по стеку работает (80 Б, стек 16 КБ), но облагает аллокацией каждый переход каждой FSM, включая тривиальные in-memory (4,9 → 22,4 нс). Как умолчание для существующих пользователей неприемлемо — отсюда две политики (§2.1), а не одна |
| Оставить обёртку на совести потребителя | Текущее положение дел. Не проверяется ничем, один пропуск обнуляет эффект: размер считается по `max` |
| Выбирать оптовую политику атрибутом `#[fsm(boxed_dispatch)]` вместо возможности сборки | Рассматривался и отвергнут в пользу feature. Атрибут — третий knob к двум уже существующим, при этом решает ту же задачу, что и пометки переходов, только грубее. Feature даёт переключение без правки исходников — в том числе в чужих крейтах, куда потребитель не может дописать атрибут |
| Поднять `thread_stack_size` у потребителя | Маскировка. Стоимость линейна по числу worker-потоков, порог всё равно определяется самым тяжёлым обработчиком и растёт вместе с ним |
| Требовать от обработчиков `-> BoxFuture<'_, T>` в сигнатуре | Ломающее изменение публичного контракта; вся эргономика `#[fsm]` держится на обычных `async fn` |
| Разбивать FSM на несколько мелких | Не решает: размер определяет самый тяжёлый обработчик, а не их количество (замер: 8 обработчиков ≈ размер одного) |

## 4. Критерии приёмки

| # | КОГДА | ТОГДА |
|---|-------|-------|
| 1 | Тяжёлый переход помечен `#[on(..., boxed)]`, возможность `boxed-all` выключена | `size_of_val` future от `apply` не превышает 256 Б независимо от тела этого обработчика |
| 2 | В FSM добавлен новый тяжёлый переход, помеченный `boxed` | Размер future от `apply` не вырос |
| 3 | Ни один переход не помечен, `boxed-all` выключена | Сгенерированный код и производительность неотличимы от версии 0.1.7 |
| 4 | Возможность `boxed-all` включена, ни один переход не помечен | Размер future от `apply` не превышает 256 Б для той же FSM, что в критерии 3 |
| 5 | Возможность `boxed-all` включена, часть переходов помечена `boxed` | Собирается без предупреждений, результат тот же, что в критерии 4; пометки безвредны |
| 6 | Возможность `boxed-all` переключается в любую сторону | Наблюдаемое поведение не меняется: порядок каскада, состояния, значения ошибок идентичны |
| 7 | Помеченная FSM выполняет переход | Порядок каскада self-emit и семантика ошибок не изменились |
| 8 | `boxed` указан на fallible-обработчике или на обработчике с payload | Работает одинаково; `ApplyError::Handler` формируется как прежде |
| 9 | Тест с потоком `stack_size = 64 КБ` и обработчиком с локалами 3 × 512 КБ | Проходит при любой из двух политик, боксирующих этот переход; падает, когда переход не боксируется ни одной |
| 10 | `cargo test`, `cargo test --features boxed-all`, `cargo clippy --all-targets` | Зелено, без новых предупреждений |
| 11 | Атрибут написан с опечаткой (`boxxed`) | Внятная ошибка компиляции с указанием на атрибут (trybuild-тест) |

## 5. Влияние на производительность

| Ситуация | Эффект |
|---|---|
| Боксируемый переход (помечен либо включена `boxed-all`) | Одна аллокация в куче на срабатывание, ~+18 нс |
| Небоксируемый переход | Без изменений (замерено: 7,5 → 7,1 нс, в пределах шума) |
| Стек | Перестаёт зависеть от тела боксируемых обработчиков |
| Размер кода | Без изменений: `Box::pin` не порождает `dyn`-диспетчеризации |

## 6. Влияние на спецификацию

Целевая спека — `openspec/specs/statecraft/statecraft.md`, версия поднимается
с 1.0 до 1.1. Вносится:

- **4.3.4** — раздел переписывается. Сегодня он фиксирует ограничение
  («кадр стека пропорционален телу самого объёмного обработчика») в форме
  осведомлённости, со ссылкой на это изменение. После применения формулировка
  становится требованием:

  > Обработка одного события FSM выполняется с ограниченным потреблением стека,
  > не зависящим от размера тела обработчика перехода. Для переходов,
  > размещаемых в куче, работа обработчика не входит в кадр стека
  > диспетчеризации. Политика размещения выбирается на этапе сборки; по
  > умолчанию в куче размещаются только явно помеченные переходы.

  Таблица замеров остаётся — она документирует цену **не**помеченного тяжёлого
  перехода, которая никуда не девается.
- **2.8** — две строки в таблице конфигурации: возможность сборки `boxed-all` и
  возможность сборки `diagnostics`.
- **2.5** — параметр `boxed` в перечне параметров атрибута перехода.
- **4.2** — строка о стоимости боксируемого перехода (одно размещение в куче,
  ~+18 нс) со ссылкой на 4.3.4.
- **4.4** — снимается оговорка «диагностических средств измерения кадра стека
  библиотека сегодня не предоставляет».
- **3** — критерии приёмки 1, 2, 4, 6, 9 из §4 настоящего change.

Формулировки в спеке намеренно не называют язык и конкретный механизм
(`Box::pin`): спека фиксирует требование, а не приём реализации. Приём описан
здесь и в `design.md`.
